# TrainDriverApp (рабочее название — «Крис»)

Android-приложение для машиниста локомотива (аналог УСАВП/ИСАВП-РТ). На экране устройства
приложение называется «Крис» (может ещё поменяться); `TrainDriverApp` — кодовое имя самого
проекта/репозитория, менять не стал, чтобы не переименовывать пакет и Gradle-модули без нужды.

## Что уже сделано (шаг 1)

Самый первый шаг: GPS показывает текущую координату в формате **км+пк**, без какого-либо
оформления экрана — просто крупный текст на чёрном фоне.

Как это работает:

1. `location/GpsLocationProvider.kt` — получает координаты через стандартный `LocationManager`
   (провайдер `GPS`), без Google Play Services и без интернета — приложение должно быть полностью
   автономным (ТЗ, раздел 2).
2. `route/RouteTrack.kt` — проецирует GPS-точку на ближайший отрезок полилинии пути и возвращает
   пикетаж (расстояние от начала маршрута в метрах).
3. `route/ChainageFormatter.kt` — переводит пикетаж в формат "км+пк". **Формула ниже —
   исправленная** (см. шаг 8): обычный км+пк по умолчанию — `км = floor(метры/1000)` (без +1),
   `пк = floor(метры_в_км / 100) + 1`; отдельно, по тапу на координату, включается формат
   КЛУБ-У — `км = floor(метры/1000) + 1` (это и есть формула с примерами из ТЗ:
   `0000.050 → 1км 1пк`, `6234.670 → 6235км 7пк` — она про КЛУБ-У, не про обычный км+пк).
4. `MainActivity.kt` — запрашивает разрешение на геолокацию и выводит результат в `TextView`.

### Важно: калибровка км — ПРИБЛИЗИТЕЛЬНАЯ, нужна проверка

У GPS-линии из OSM нет привязки к реальным номерам километров РЖД — только форма пути. У профиля
пути в PDF (`Хилок-Крм.pdf`, `Крм-Чернышевск.pdf` и т.д., которые ты прислал) есть реальные номера
км, но нет GPS. Пока сделано так:

- начало маршрута (ближайший к Хилоку узел линии) считается точкой **км 5930** — это число просто
  прочитано с левого края первой страницы `Хилок-Крм.pdf`, где начинается участок с станцией Хилок;
- построенная по OSM линия короче, чем разница реальных км по профилю (642.8 км против 659 км
  между Хилоком и Чернышевском) — это ожидаемо, т.к. OSM хранит сглаженную/упрощённую форму пути.
  Введена единая поправка на длину `659 / 642.8 ≈ 1.025` (`RouteTrack.HILOK_CHERNYSHEVSK_LENGTH_CORRECTION`),
  чтобы компенсировать это в среднем по всему маршруту;
- совпадение общей длины (642.8 км по факту против 659 км по профилю, расхождение ~2.5%) — хороший
  знак, что путь построен правильно (не перепутана ветка на разъезде и т.п.), но это не то же самое,
  что точная калибровка каждого пикета.

**Что нужно от тебя, чтобы довести до точности:** одна-две проверенные пары "GPS-точка ↔ реальный
км+пк" (например, встань на сигнале с известным км+пк и посмотри, что показывает телефон). По ним
можно будет поправить `HILOK_START_KM` и коэффициент коррекции и проверить, что ошибка не растёт
к концу маршрута.

Также пока не реализовано: выбор направления (чётное/нечётное) и различение правильного/
неправильного физического пути (ТЗ, раздел 3) — сейчас пикетаж всегда считается по одной линии.

## Шаг 3: разобраны постоянные ограничения скорости

Из `скорости все новые.xlsx` (набирался вручную с бумажных документов дороги, поэтому формат
неоднородный) вычленены постоянные ограничения скорости для основного пути на нашем перегоне,
для гружёных поездов серий 3ЭС5К/ВЛ85 — это данные для «ступенчатого графика скорости» (ТЗ,
раздел 7).

- Взяты 4 листа: `Хилок-КРМ`, `КРМ-Хилок`, `КРМ-Черн`, `Черн-КРМ` (по два на направление —
  чётное/нечётное, пикеты растут/убывают, см. ТЗ раздел 3). Остальные листы файла (`Хилок-ПЗВ`,
  `КРМ-Олов` и т.п.) — это другие перегоны, не наш маршрут, не трогали.
- Из каждой строки берётся диапазон км+пк (колонка «Станция/перегон») и скорость для 3ЭС5К/ВЛ85 —
  остальные колонки (скорость по стрелкам/приёмо-отправочным путям, обрывные места, проба
  тормозов, осмотр поезда, порожние вагоны) пока не трогаем, они для отдельных функций
  (пиктограммы, оповещения) и разберём их позже.
- Результат — `app/src/main/assets/speed_limits.json`, 411 диапазонов. В код ещё не подключено —
  экрана, который бы это показывал, пока нет.
- Сборка воспроизводима: `tools/parse_speed_limits.py "скорости все новые.xlsx" app/src/main/assets/speed_limits.json`.

### Важно про эти данные

- **Иерархия диапазонов.** У каждого перегона/станции есть «общая» строка на весь блок
  (например «Хилок - Гыршелун (5935 пк 3 - 5950 пк 7)» → 80 км/ч) и более узкие строки-исключения
  внутри неё (например «5942 пк 5 - 5943 пк 7» → 60 км/ч) — обе попали в список как есть. Значит,
  при использовании этих данных нужно сначала искать САМЫЙ УЗКИЙ подходящий диапазон и только
  если ни один не подошёл — брать общий. Логику выбора ещё не писал.
- **6 опечаток в исходном файле** (кириллические "З"/"б" вместо цифр "3"/"6" — например
  "6124 пк З", "б376") — скрипт их поправил, водитель подтвердил все шесть по бумажному
  оригиналу: `6123 пк2-6124 пк3`, `6277 пк10-6279 пк3`, `6292 пк8-6293 пк3`, `6053 пк3-6014 пк9`
  (Могзон - Тайдут), `6393 пк8-6376 пк10` (Размахнино - Зубарево), `6305 пк10-6302 пк3` (Тарская -
  Карымская).
- **Битая ячейка на участке 6159 пк 2 - 6162 пк 8** (лист Хилок-КРМ, в файле вместо числа стояло
  `'S()'`) — водитель подтвердил, что там 80 км/ч; исправление зашито в `KNOWN_CORRECTIONS` в
  скрипте, со ссылкой на то, что это подтверждено по бумажному документу, а не подобрано скриптом.
- **4 строки без понятной скорости** — не попали в итоговый файл, это станционные/стрелочные
  уточнения, чья скорость лежит в другой колонке (см. ниже про «Путь 4» и т.п.).
- **51 строка вида «Путь 4», «стр. №37», «съезд 5-7»** — это уточнения скорости для конкретного
  станционного пути/стрелки, без своего диапазона км+пк (он берётся из строки-заголовка станции
  выше). Не попали в файл — они не нужны для скорости по ходу главного пути, пригодятся позже для
  вкладки станций/путей, если понадобится.

## Шаг 4: разобраны условные предупреждения о жёлтом сигнале

Из `сигналы_желтый_чётное.xlsx` и `сигналы_желтый_нечётное.xlsx` — список правил вида «если
после сигнала [От] следующий сигнал [До] покажет жёлтый, скорость проследования не выше [X]
км/ч» (ТЗ, раздел 6 / «Условное предупреждение про жёлтый сигнал»). В отличие от файла со
скоростями, эти два размечены аккуратно, обычными колонками — разбор занял минуты, без
regex-эквилибристики и опечаток.

- 96 строк (чётное) + 61 строка (нечётное) = 157 — точно совпадает с числом из ТЗ.
- Все строки разобрались без проблем, пропусков и битых значений не нашлось.
- Результат — `app/src/main/assets/yellow_signal_warnings.json`, воспроизводится
  `tools/parse_yellow_signals.py yellow_signal_warnings.json <папка с исходными xlsx>`.
- 4 из 157 записей помечены «по неправильному пути» (`wrong_path: true`) — они срабатывают,
  когда состав идёт по неправильному физическому пути (ТЗ, раздел 3).

### Важно: не хватает привязки сигналов к км+пк

В этом файле сигналы названы литерами («Ч», «ЧМ2А», «т.11» и т.п.) и станциями/перегонами, но
**без** координаты км+пк — только длина блок-участка в метрах. Чтобы функция реально
срабатывала по GPS-позиции (при вступлении на блок-участок перед сигналом «До»), нужно ещё
знать, на каком именно пикете стоит каждый сигнал «От». Этого сопоставления сигнал → км+пк
пока нет нигде в присланных данных.

**Решение:** делаем эту привязку не сейчас отдельно, а вместе с главным экраном (ТЗ, раздел 7) —
там всё равно придётся построчно разбирать те же профили пути в PDF (ступенчатый график,
пиктограммы, рельеф), и координаты сигналов естественно появятся по ходу дела.

Термины сигналов (от машиниста, для справки):
- **т.NN** («точки») — перегонные светофоры без буквенной литеры; номер убывает к станции по
  правильному пути (14, 12, 10... чётное; 15, 13, 11... нечётное, см. ТЗ раздел 4).
- **Ч / Н** — входные сигналы станций (по правильному пути); **ЧД / НД** — то же, по
  неправильному пути.
- **ЧМ / НМ** — маршрутные сигналы, делят станцию на участки (горловины, парки).
- **Ч2 / Н1** (буква + число, без «М») — выходные сигналы станций.

## Шаг 5: разобраны точки пробы тормозов

Из `Пробы_тормозов.xlsx` (листы `Хилок-КРМ` и `КРМ-Черныш` — остальные листы того же файла
покрывают другие участки дороги, не наши) — список точек, где нужно выполнять пробу тормозов
(ТЗ, раздел 6, оповещение «Впереди проба тормозов!» за 2000 м до точки).

- Результат — `app/src/main/assets/brake_tests.json`, 42 точки (26 чётных + 16 нечётных, из
  них 5 — для сдвоенного поезда). Воспроизводится
  `tools/parse_brake_tests.py "Пробы_тормозов.xlsx" app/src/main/assets/brake_tests.json`.
- Данные чистые, без опечаток и пропусков — разбор занял пару минут, как и с сигналами.

### Как это устроено (пояснения машиниста)

- **км+пк в списке — координата самой пробы**, а не точки объявления; объявлять нужно за
  2000 м до неё (это уже знали из ТЗ, теперь подтверждено).
- **Скорость вида «55/60»** — это диапазон (55–60 км/ч), внутри которого проба тормозов
  засчитывается; вне диапазона нужно ждать следующую точку. Если диапазонов несколько
  («45/50 55/60 65/70» на «Гонгота-Сохондо») — подходит любой из них.
- **Строки «(сдвоен.)»** — отдельная, другая точка пробы специально для сдвоенного поезда
  (не тот же километр с другим текстом объявления). Как машинист будет отмечать в приложении,
  что поезд сдвоенный, — пока не решено, будет отдельная настройка позже.
- **Этот список — источник истины.** Если режимная карта (профиль пути в PDF) показывает пробу
  тормозов в другом месте — верить нужно этому списку, а не карте: на картах пробы бывают
  указаны неправильно.

## Шаг 6: логика направления и правильного/неправильного пути

`route/DirectionSelection.kt` реализует таблицу из ТЗ (раздел 3 / «УСАВП-аналог_ИТОГ.pdf»
раздел 4): машинист вручную выбирает направление (чётное/нечётное) и физический путь (1 или
2) — из этой пары выводится:

- **правильный/неправильный путь** — чётное+путь2 и нечётное+путь1 правильные, остальные два
  сочетания неправильные;
- **какой датасет использовать** (поле `direction` в speed_limits.json /
  yellow_signal_warnings.json / brake_tests.json) — на практике сводится к тому, что путь 1
  всегда означает нечётный датасет, путь 2 — чётный, независимо от выбранного направления;
- **растут пикеты или убывают** — зависит только от направления (чётное — растут, нечётное —
  убывают), не от пути.

Km+пк по GPS при этом никак не меняется в коде в зависимости от направления — `RouteTrack`
просто отражает физическую позицию на пути, которая сама по себе растёт или убывает в
зависимости от того, куда реально едет поезд. Направление здесь нужно только чтобы понять,
какой из двух датасетов (собранных отдельно для чётного/нечётного) сейчас использовать при
поиске скоростей/сигналов/проб тормозов — см. следующий шаг, там это уже подключено для
скоростей.

Пока сделаны только две кнопки-переключателя на временном экране (не финальный вид, просто
чтобы проверить логику): «Чётное/Нечётное» и «Путь 1/Путь 2», плюс строка с результатом
(«Путь правильный, датасет: чётный, пикеты растут»). По умолчанию — чётное, путь 2.

## Шаг 7: главный экран, первый срез — линейка и ступенчатый график скорости

Начали главный экран (ТЗ раздел 7) с того, на чём держится всё остальное — километровая/
пикетная линейка и ступенчатый график постоянных ограничений скорости, поверх которых потом
встанут сигналы, пиктограммы и профиль рельефа.

- `route/SpeedLimit.kt` / `SpeedLimitAssetLoader.kt` — читают speed_limits.json, переводя
  км+пк в метры через новую `ChainageFormatter.toMeters()` (обратную к `format()`).
- `route/SpeedLimitResolver.kt` — по позиции (в метрах) и направлению возвращает действующее
  ограничение; если подходит и общая, и более узкая строка-исключение (см. шаг 3) — побеждает
  самая узкая, как и было задумано.
- `ui/TrackProfileView.kt` — кастомная View: рисует ступени (серая заливка от 100 км/ч вниз
  до значения лимита — как в ТЗ, «не снизу вверх»), километровую сетку с номерами км по
  центру столбца (как на профилях пути), пикетные деления и вертикальный маркер позиции
  поезда. Окно обзора — 3000 м позади / 5000 м впереди головы, как в официальном описании
  экрана ИСАВП-РТ (`основное_окно_сокр.pdf`).
- Подключено в `MainActivity` — при каждом обновлении GPS обновляется и позиция на графике;
  при переключении направления/пути (шаг 6) — какой датасет (чётный/нечётный) показывать.

### Исправление: сверка с реальным макетом (раздел 14 ТЗ)

Первая версия этого шага была построена только по текстовому описанию раздела 7 — я не
прочитал страницы 8–14 самого первого ТЗ-файла (14 страниц всего), где как раз лежит раздел
14 "Приложение: полный набор изображений макетов" с реальными картинками главного экрана.
Из-за этого первая версия сильно недотягивала до макета: не было шапки, чисел на самих
ступенях, шкалы скорости слева, нижней строки статуса. Прочитал эти страницы, поправил:

- `SpeedLimitResolver.findNextChange()` — ищет ближайшую впереди точку, где меняется
  скорость (нужно для ячейки "V=.../S=..." нижней строки статуса).
- `TrackProfileView` — добавлены шкала скорости слева (100/80/60/40/20) и число скорости
  прямо на каждой ступени (крупным белым по центру), как на макете.
- Шапка (`MainActivity`, `activity_main.xml`) — координата слева, время МСК и местное справа
  (местное — из часового пояса телефона, обновляются раз в секунду по-настоящему, не заглушка).
- Нижняя статусная строка (5 ячеек по ТЗ): Vф — настоящая скорость по GPS; V=/S= — настоящий
  расчёт через `findNextChange`; Уклон/Голова/Хвост — пока "—", для них нужны данные о
  рельефе пути и о км+пк сигналов, которых ещё нет (см. шаг про сигналы).
- Живой HTML-макет в чате обновлён тем же способом — можно посмотреть без сборки APK.

## Шаг 8: исправлен формат км+пк — путали с КЛУБ-У

Нашлась серьёзная ошибка: в ТЗ (раздел 7) написано "Координата (км+пк, **по тапу
переключается в формат КЛУБ-У**)" — то есть это ДВА РАЗНЫХ формата. Формула с примерами
(`km = floor(значение)+1`, `0000.050 → 1км 1пк`) — это именно формат **КЛУБ-У**, отдельный,
включаемый только по тапу. А обычный км+пк (тот, что должен быть по умолчанию, и тот, которым
записаны все таблицы — например "Хилок (5932 пк 7 - 5935 пк 3)" в speed_limits.json) — БЕЗ
+1: `км = floor(метры/1000)`.

Раньше `ChainageFormatter` использовал формулу КЛУБ-У как единственную и универсальную —
из-за этого:
- координата в шапке показывала км на 1 больше реального;
- что важнее — `SpeedLimitAssetLoader` использовал ту же (неверную) формулу для перевода
  км+пк из speed_limits.json в метры, поэтому весь график ограничений скорости был физически
  сдвинут на 1000 м относительно реальной GPS-позиции. Это, видимо, и была основная причина
  «совсем не похоже на ТЗ» — график и координата не совпадали друг с другом даже там, где
  форма была правильной.

Исправлено:
- `ChainageFormatter.format()` — теперь обычный км+пк (без +1), формат по умолчанию;
- `ChainageFormatter.formatKlubU()` — новый метод, старая формула с +1, для формата КЛУБ-У;
- `ChainageFormatter.toMeters()` — тоже без +1/-1, обратное к обычному км+пк (так как именно
  в этом формате записаны все остальные данные);
- клик по координате в `MainActivity` теперь переключает обычный км+пк / КЛУБ-У, как в ТЗ;
- километровые подписи на графике (`TrackProfileView`, HTML-превью) — тоже без +1.

## Шаг 9: зафиксированы точные чертежи пиктограмм (ТЗ раздел 8)

Машинист прислал реальные чертежи с размерами (мм) для нескольких значков — ниже цифры,
которые считаются окончательными и **не подлежат пересогласованию** без нового чертежа.
Реализовано пока только в HTML-превью (`drawPictogramGlyph` и соседние функции в
`preview.html`); при переносе на Android (`TrackProfileView.kt` или отдельный
`PictogramIcons.kt`) — использовать те же соотношения мм, не рисовать на глаз.

**КТСМ** — равносторонний треугольник, сторона 140мм, вершиной вниз:
- 3мм чёрного поля от внешнего края → белая окантовка 4мм → чёрное поле внутри;
- внутри — одна сплошная V-образная лента (не буква V шрифтом, не два отдельных бруска):
  толщина 14мм постоянная по всей длине (лента строится через параллельный сдвиг боковых
  сторон треугольника на фиксированное перпендикулярное расстояние — 16мм от края до
  внешнего края ленты, 30мм до внутреннего, — а не масштабированием по x, иначе толщина
  плывёт к вершине);
- сверху лента срезана параллельно верхней грани на 16мм от края (7мм окантовка + 9мм);
- острый угол схождения внизу, острая выемка вверху между "рогами" — оба угла получаются
  автоматически как пересечения соответствующих линий, без отдельной подгонки.

**Опасное место / начало и конец временного ограничения** — круг Ø550мм:
- белый круг, чёрное кольцо-обод 100мм толщиной, внешний край кольца вплотную к краю
  круга (без отступа);
- чёрная перекладина через центр, той же толщины (100мм);
- световозвращатели (белые точки) Ø51мм: 8 штук по кольцу на позициях циферблата
  (12, 1:30, 3, 4:30, 6, 7:30, 9, 10:30 — начиная строго с 12 часов, по часовой стрелке)
  + 3 в перекладине = 11 одного размера; 5 точек на центральной горизонтали (2 крайние
  от кольца + 3 от перекладины) стоят равномерно;
- «конец опасного места» — тот же значок, повёрнутый на 90° по часовой стрелке;
- эта же иконка (без изменений) используется в шапке экрана как кнопка вызова ввода
  ограничений — единая иконка на всё, не отдельная самодельная упрощённая версия.

**Жёлтый щит / зелёный щит** — квадрат, сторона 470мм:
- белая рамка 25мм → чёрная рамка 25мм (РАВНЫ друг другу, не "чёрная вдвое толще" —
  это было неверное предположение по одному только тексту ТЗ, исправлено по чертежу)
  → цветная (жёлтая/зелёная) заливка внутри, 370мм, самая большая по площади.

**Нейтральная вставка (отключить ток)** — синий ромб (сторона 450мм по чертежу знака
"включить ток", тот же ГОСТ, но одинарный ромб, не сдвоенный):
- белая окантовка 20мм СНАРУЖИ → чёрная окантовка 20мм → синяя заливка (оба слоя даны на
  чертеже как два отдельных "20", не одна и та же линия дважды — типичная ошибка, которую
  стоит проверять на любом похожем чертеже: если рядом стоят два одинаковых числа с
  отдельными выносками, это почти всегда два разных слоя, не дубль одного);
- плюс тонкий серый контур снаружи белой окантовки (отдельно, из более раннего описания
  ГОСТ 8442-65);
- внутри — 2 белых скруглённых квадрата 90×90мм с зазором 80мм между ними, и такой же
  зазор 80мм от квадратов до полосы снизу (полоса шириной 260мм = 2×90+80, радиус
  скругления углов 40мм) — НЕ перевёрнутая П, три отдельные фигуры;
- все фигуры внутри — пустые, без кружков (в оригинальном путевом знаке они есть, но по
  требованию машиниста убраны).

**Проба тормозов (НТ), мост, переезд** — точных чертежей с размерами не присылали, формы
оставлены как есть (белый квадрат/красная окантовка + буквы «НТ»; треугольник с красной
окантовкой, белая заливка, чёрный символ моста/шлагбаума внутри) — не считать финальными
в том же смысле, что остальные три.

## Шаг 10: калибровка GPS → км+пк по реальным точкам машиниста

Машинист прислал GPS-якоря вида "координата → реальный км+пк", как раз то, что запрашивалось
в шаге 2. Проверка на `route_hilok_chernyshevsk.json` (см. `RouteTrack.kt`):

- **51.359412, 110.462016 → 5934км 7пк** — 156 м от линии маршрута. Хорошо.
- **51.940295, 113.619818 → 6213км 5пк** — 6.8 м от линии. Отлично.
- **52.501740, 117.004039 → 6585км 3пк** — перепроверена машинистом дважды (координата
  практически не изменилась), но ближайшая точка на всей линии всё равно в **47.6 км**.
  Причина — не опечатка: самая северная точка во ВСЁМ файле `route_hilok_chernyshevsk.json`
  имеет широту 52.2549°, а эта GPS-точка — 52.5017°, то есть севернее любой точки маршрута.
  Линия физически не доходит досюда. Похоже, либо `export.geojson` обрывается раньше реального
  конца перегона, либо при сборке пути по графу (шаг 2) на каком-то разъезде в последних

  построенная линия расходится с реальным путём.

По первым двум (надёжным) точкам решена система из двух уравнений `реальный_км = старт +

- `HILOK_START_KM`: 5930.0 → **5934.65** (раньше — на глаз с левого края PDF-профиля, теперь —

- `HILOK_CHERNYSHEVSK_LENGTH_CORRECTION`: 659/642.8 ≈ 1.025 → **0.9967** (раньше — грубая оценка

Калибровка опирается только на два якоря у хилокского конца маршрута (0 км и ~280 км по линии

судя по всему, имеет отдельный дефект (см. выше) — его нужно чинить в самих данных пути, а не

## Шаг 13: разобраны два открытых вопроса шага 12 (средний путь, расхождение направлений)

Машинист объяснил оба открытых вопроса шага 12:

**«Средний» — это третий путь, а не вариант тормозного коэффициента.** На перегоне
Тургутуй — Яблоновая три пути (нечётный, чётный и средний), и по среднему поезда могут идти в
обоих направлениях — поэтому на профиле у него свои светофоры, которые просто совпадают по
номеру с светофорами основного пути в той же точке. Это не дубль одной записи, а два разных
физических светофора. Раньше скрипт схлопывал их в один по (литера, км, пк) — теперь такая
запись (обнаруживается по подписи «средний» под номером, вплотную) помечается
`"track": "средний"` и не схлопывается с одноимённым сигналом основного пути.
Затронуло 9 записей (5 на странице Тургутуй — Яблоновая в `Хилок-Крм.pdf`, 4 в `Крм-Хилок.pdf`),
из них только 3 реально были схлопнуты раньше (остальные и так не совпадали по пикету) —
итоговый счётчик вырос всего на 3 (1336 → 1339).

**Расхождение ~17% между Хилок-Крм.pdf и Крм-Хилок.pdf — не ошибка.** Проверил конкретные
случаи: например «Н1» на 5951км 3пк есть только в `Крм-Хилок.pdf` — это выходной светофор,
нужный только поезду, уходящему в нечётном направлении, поэтому во встречном документе его
просто нет (он там не нужен, а не потерян). Входные/выходные литеры станций (голая Ч/Н,
буква+число) рисуются только в документе своего направления; голые числа автоблокировки и
предвходные ЧД/НД, актуальные для обоих направлений, совпадают между документами почти всегда
(это они и дают основную долю тех самых 83%). Оба документа — не конфликтующие версии одной
истины, а взаимно дополняющие наборы, поэтому оставлены как есть, оба со своим `source`.

- **37** — записи вида «ЧМ32 - ЧМ37» (диапазон нескольких сигналов одной горловины, а
  не один сигнал) — км+пк одной точки для них не определить без потери смысла. Помечены

- **11** — реально сопоставлены (2 однозначно по уникальной литере, 9 — по ближайшей

## Шаг 15: форма рельефа извлечена из тех же профилей — но без калибровки в метры

Рельеф на профилях — не текст, а чёрная волнистая векторная кривая (PyMuPDF
`page.get_drawings()`), поэтому разбирается отдельным скриптом `tools/extract_relief.py`,
не текстовым `parse_track_profile.py`: находим самый широкий (>85% ширины страницы)
почти-чёрный векторный путь с заметной высотой (тем же пером, что рисует иконки
светофоров) и сэмплируем его отрезки/кривые Безье в точки, дальше — та же сетка
км+пикет, что и у сигналов. Проверил визуально на двух разных документах (наложил
извлечённую кривую поверх рендера страницы) — совпадает с рельефом пиксель в пиксель.

**Куда более серьёзное открытие, чем сама механика извлечения:** на этих страницах
вообще нет шкалы высот — ни оси, ни легенды с масштабом, только сам рисунок. Хуже того,
высота в pt даже НЕ сравнима между соседними страницами одного документа: на границе
каждых двух страниц (одна и та же физическая точка пути) разрыв высоты доходит до
60+ pt, хотя реальный перепад между соседними пикетами (100-200 м) заведомо не может
быть такой резкой ступенькой. Значит, каждая страница рисуется со своим независимо
подобранным вертикальным масштабом — не единым на весь маршрут, — и сшить их в один
сквозной график поправкой на постоянное смещение нельзя (плавает не только сдвиг, но
и масштаб). Высоты этого шага честны и точны только В ПРЕДЕЛАХ ОДНОЙ СТРАНИЦЫ
(`source`+`page`), не более того.

На практике это не так страшно, как звучит: видимое окно графика в приложении — это
~4.6 км, а не 14-15 км одной страницы целиком, так что почти всегда весь нужный кусок
рельефа лежит на одной странице; сшивка нужна только у самой границы, и это отдельная,
не решённая здесь задача.

- Результат — `app/src/main/assets/track_relief.json`, 13799 точек, 92 из 94 страниц
  (не считая страницу 12 `Хилок-Крм.pdf` — сложная станция Тургутуй — Яблоновая, кривая
  рельефа там не находится, видимо разбита посторонней станционной графикой).
- Воспроизводится: `tools/extract_relief.py <папка с исходными PDF> app/src/main/assets/track_relief.json`.
- Не сделано: реальная физическая величина для расчётов (сопротивление движению и т.п.)
  — это не форма рельефа, а уклон (‰) из красной зубчатой строки под км-рядом на тех же
  страницах. Там свои числа (значит, не нужна калибровка в метры), но не разобрался
  надёжно со знаком (подъём/спуск) каждого числа по рисунку зубца — сознательно не стал
  гадать и оставил как отдельную, ещё не начатую задачу.

## Шаг 16: разгадка «нестыковки» страниц шага 15 — это не баг, а как рисует сам экран

Машинист объяснил независимый масштаб/сдвиг каждой страницы из шага 15: это не артефакт
экспорта PDF, а точное описание того, как ведёт себя рельеф на настоящем экране —
"когда профиль поднимается выше линии, вся линия целиком опускается, чтобы не выходить
за пределы верхней границы, и так едет дальше". То есть реальный экран не показывает
рельеф в одном сквозном масштабе — он панорамирует (сдвигает целиком, не сжимая форму)
видимый кусок так, чтобы самая высокая точка в текущем окне не вылезала за потолок. Раз
так работает настоящий экран, глобальная калибровка в метры (то, что не получилось
сделать в шаге 15) вообще не нужна — куда важнее не абсолютная высота, а именно это
поведение при отрисовке.

Реализовал это в макете (`preview.html`): вместо прежней иллюстративной синусоиды рельеф
на участке км5930-5944 (реальные данные шага 15, `Хилок-Крм.pdf` стр.1, чётное) теперь
рисуется по-настоящему, с этим же панорамированием — на каждой отрисовке ищется максимум
реальной высоты в текущем видимом окне (~4.6 км) и весь рельеф сдвигается так, чтобы этот
максимум лёг вплотную к потолку полосы (`REAL_RELIEF_PX_PER_PT`/`ceilingY` в
`reliefY()`) — не масштабирование (форма и крутизна холмов не меняются), а именно
сдвиг, как описано. За пределами км5930-5944 (данных другой страницы нет, см. шаг 15) —
по-прежнему прежняя иллюстративная синусоида, стык между ними виден, но не выглядит
сломанным.

- Проверено: при движении слайдера через невысокий участок (км5932-5934) рельеф
  занимает низ полосы; когда в окно попадает самая высокая точка страницы (км5941.5,
  63.6pt — самый высокий пикет на всей странице), рельеф вырастает почти до потолка —
  именно так, как машинист описал поведение настоящего экрана.

## Шаг 17: реализована и протестирована логика «короткого участка повышенной скорости»

ТЗ раздел 9: если короткий участок с БОЛЕЕ ВЫСОКОЙ скоростью зажат между двумя другими и его
физическая длина короче длины поезда — состав физически не может там разогнаться (часть
состава всё ещё на соседнем участке всё время прохождения короткого отрезка). Эффективная
скорость — МАКСИМУМ из скоростей двух соседних участков, причём не обязательно предыдущего
и не обязательно меньшего (в ТЗ два examples ровно на этот случай: 60→70(коротко)→50 даёт
60, а 50→80(коротко)→65 даёт 65 — от СЛЕДУЮЩЕГО участка, а не предыдущего).

Новый `ShortSegmentSpeedResolver.kt`: сначала точно (не сэмплированием, а по границам самих
диапазонов) восстанавливает кусочно-постоянный профиль скорости из перекрывающихся
общих/узких записей `speed_limits.json` — то же самое, что резолвит `SpeedLimitResolver` в
каждой точке, но целиком, отрезок за отрезком, со склейкой одинаковых соседних. Затем для
каждого внутреннего отрезка проверяет: короче ли он `trainLengthM` (параметр запроса, а не
поле состояния — длина состава может поменяться посреди рейса, ТЗ раздел 5) и выше ли он
ОБОИХ соседей — только тогда это тот самый случай, и `effectiveSpeedKmh` = максимум соседей;
если между отрезком и соседом есть разрыв в данных (не встык) — не считается «зажатым»,
не подставляется наугад.

- Тесты (`ShortSegmentSpeedResolverTest.kt`) — оба примера из ТЗ дословно, плюс отрицательные
  случаи (отрезок не короче состава; короткий, но НЕ выше обоих соседей — это уже обычное
  ограничение, не раздел 9; отрезок в начале/конце данных без одного из соседей; разрыв между
  отрезками), плюс перепроверка на настоящих числах из `speed_limits.json` (Хилок, чётное):
  участок 6105.9-6106.0км — 100 м на 80 км/ч зажаты между 60 и 60 — короче почти любого
  реального состава.
- Заодно нашёл в самих данных: в `speed_limits.json` десятки таких "островков" по всему
  маршруту короче 2 км (например 100, 100, 200, 300, 500, 700, 800, 900×2, 1000, 1100,
  1200, 1300×2 м) — это не гипотетический краевой случай ТЗ, а частая реальная ситуация на
  этой дороге, так что раздел 9 действительно нужен, а не только "для полноты".
- Не сделано (на момент этого шага): реального класса состава/его длины в метрах не было
  нигде в коде — закрыто следующим шагом. Отрисовка зеркальной штриховки «\» на графике (ТЗ
  описывает её отдельно от обычной «/» у временных ограничений) — по-прежнему не сделана ни
  в макете, ни в реальном экране.

## Шаг 18: длина состава в метрах — формула и полоска поезда по-настоящему

Машинист подтвердил формулу перевода «условной длины» состава (ТЗ раздел 5, поле «Условная
длина» в «Параметры», единица — усл. вагоны) в физические метры: **усл. вагоны × 14 м +
длина локомотива**. 14 м — это стандартная железнодорожная единица условного вагона, а не
то же самое, что число физических вагонов (у машиниста они могут не совпадать — гружёные и
порожние вагоны разной длины считаются в условных по-разному).

Новый `TrainComposition.kt`: та же таблица серий локомотивов, что в HTML-макете (`Э5К` ...
`ВЛ80р(3)`), плюс `TrainComposition(locomotiveSeries, conditionalLengthUslVag).lengthM` по
этой формуле. Проверено тестом на дефолтных значениях самого макета (3ЭС5К + 58 усл.ваг. =
864.5 м).

Это ровно та величина, которая нужна в двух местах:
1. **Раздел 9** (шаг 17) — `ShortSegmentSpeedResolverTest`, тест на реальных данных, раньше
   использовал грубое приближение "число физических вагонов × 14" (613 м) — на самом деле
   нужна была условная длина, а не физическое число вагонов; тест переписан на
   `TrainComposition` с настоящей формулой (864.5 м).
2. **Полоска поезда на графике** (ТЗ раздел 7): `TrackProfileView.setTrainLengthM()` —
   раньше на реальном экране голова поезда была просто вертикальной чертой без длины (в
   отличие от HTML-макета, где полоска уже была, но с иллюстративной константой 300 м);
   теперь рисуется полоска настоящей длины состава от головы (GPS-координата) назад, вдоль
   границы ступеней/линейки.
- `MainActivity` пока подставляет туда захардкоженное значение по умолчанию (3ЭС5К,
  58 усл.ваг., то же самое, что и в макете) — экрана «Параметры» в реальном приложении
  ещё нет, машинист пока не может ввести это сам. Заменить на реальный ввод — следующий шаг
  по этому направлению, если понадобится раньше остальных открытых вопросов.

## Шаг 20: голосовые оповещения — записаны и подключены (частично)

Машинист записал женским голосом 8 фраз из ТЗ раздел 6 (без моста — решил не обозначать
мосты вообще нигде, ни визуально, ни голосом; без условного жёлтого сигнала — там переменная
фраза, сотни сочетаний литеры и скорости, целиком не записать, это отдельная задача). Файлы
лежат в `res/raw/announce_*.mp3`.

Приём файлов был по одному, каждый явно подписан машинистом в чате — просто прочитать
название файла не вышло: сама загрузка стирает кириллицу из имени (заменяет каждую букву на
"_", проверено побайтово), поэтому имя не сохраняется вообще нигде — ни в самом файле, ни в
ID3-тегах. Побочный эффект оказался полезным: до того, как машинист продиктовал порядок,
я прикинул соответствие по длительности звучания (более длинная фраза = более длинный файл) —
и когда машинист прислал файлы в явном порядке, все 8 совпали с этой прикидкой один в один.

- `VoiceAnnouncer.kt` (новый пакет `audio`) — обёртка над `SoundPool` (не `MediaPlayer`: это
  короткие 1.5-4 сек реплики, должны звучать без задержки в момент пересечения порога
  расстояния, а не одно длинное аудио), `Announcement` enum на все 8 записанных фраз.
- `PointAnnouncementScheduler.kt` — сколько машинисту метров осталось до точки решает не он,
  общий (по `T`) разовый триггер "объявить один раз, когда точка попала в зону за N метров
  впереди по ходу движения" — не привязан к пробе тормозов специально, пригодится для любых
  будущих point-based оповещений. Тесты: срабатывает один раз при входе в зону, не повторяет
  на каждый GPS-тик внутри зоны, не объявляет задним числом точку, мимо которой уже проехали
  (например, если приложение запустили рядом с ней), работает для обоих направлений.
- **Подключена только проба тормозов** (`BrakeTest.kt`, `BrakeTestAssetLoader.kt`,
  `brake_tests.json`, шаг 5) — единственное из 6 оставшихся оповещений, для которого вообще
  есть координаты в присланных данных. За 2000 м до точки играет `BRAKE_TEST` или
  `BRAKE_TEST_DOUBLE` (по полю `double_train`) — прямо из GPS-колбэка в `MainActivity`,
  планировщик пересобирается при смене направления/пути (`updateDirectionUi`), потому что
  меняется effectiveDataset — какие именно точки вообще "впереди".
- **Остальные 5 фраз записаны и лежат в ресурсах, но играть их пока нечем**: ни для переезда,
  ни для КТСМ, ни для предвходного станции *(закрыто следующим шагом)*, ни для обрывного
  места, ни для временного ограничения нет координат ни в одном из присланных файлов — это
  не сделано специально, а физически не из чего сделать. Временное ограничение примечательно
  отдельно: сам ввод («Ограничения», ТЗ раздел 11) в реальном приложении тоже ещё не сделан,
  только в HTML-макете, так что даже пользовательских координат пока негде взять.

## Шаг 21: предвходной станции — координаты нашлись в уже разобранных данных

Оказалось, что для «Внимание! Впереди станция!» не нужны новые исходники — только правильно
понять термин. Машинист объяснил: «предвходной» — это не входной сигнал станции (Ч/Н) и не
сама станция, а последний перегонный светофор перед входным — то есть т.2 для чётного
направления и т.1 для нечётного (автоблокировка считает вниз к станции чётными/нечётными
числами, см. шаг 4/12, последняя перед входным всегда 2 либо 1). Всё это уже есть в
`track_signals.json`/`track_stations.json` (шаги 12-13) — просто раньше не был известен номер
нужной "точки".

Новый `tools/build_station_announcements.py`: та же логика привязки к ближайшей станции, что
и в `match_yellow_signals.py` (шаг 14) — литеры "2"/"1" называются одинаково у каждой станции
маршрута, поэтому берётся ближайший одноимённый сигнал к позиции самой станции. Проверил
вручную на Гыршелуне (реальные данные): т.2 нашёлся в 3100 м перед станцией на чётном, т.1 —
в 2700 м на нечётном, в обоих случаях это действительно ближайшая "точка" перед входным
сигналом, а не он сам.

- Результат — `app/src/main/assets/station_announcements.json`, **74 из 85 станций (87%)**.
  Не резолвится: Хилок (чётное) — это самое начало маршрута документа, перед ней на этой
  странице попросту ничего нет; Карымская/«Парк»/Шилка (везде) — крупные станции со сложными
  горловинами, та же причина, что и в шаге 14 для жёлтых сигналов; Яблоновая (нечётное) и
  Лесная (чётное) — без конкретной установленной причины, просто не нашлось т.1/т.2 в
  пределах допуска. Не подставлял ничего наугад — эти станции просто без записи.
- `StationAnnouncement.kt`/`StationAnnouncementAssetLoader.kt` + `stationScheduler` в
  `MainActivity` (тот же `PointAnnouncementScheduler`, что и у пробы тормозов, порог 1500 м) —
  играет `Announcement.STATION` за 1500 м до предвходного, тоже пересобирается при смене
  направления/пути.
- Воспроизводится: `tools/build_station_announcements.py` (по умолчанию читает
  `track_signals.json`/`track_stations.json` и пишет `station_announcements.json` прямо в
  assets).

## Шаг 22: окошко прибытия/отправления и история остановок (ТЗ раздел 10)

Реализована логика ТЗ раздела 10 — не отладочная панель, а реальная функция: окошко с
секундомером стоянки и отдельная панель истории прошлых остановок. Проверено на макете
(`preview.html`) headless-браузером — оба состояния (поезд стоит / только отправился) визуально
совпадают с эталонной раскадровкой из ТЗ (стр. 9-10 PDF).

- `ArrivalDepartureTracker.kt` — конечный автомат с тремя состояниями: `Hidden` (едем, окно не
  нужно), `Stopped` (стоим — верхняя строка зафиксирована, средняя считается вживую самим UI по
  разнице `now - arrivalTime`), `JustDeparted` (только отправились — нижняя строка получает
  время, средняя ЗАМОРОЖЕНА на итоговой длительности стоянки). Переход `Stopped → JustDeparted`
  сразу пишет запись в историю (`StopRecord`). Порог "поехали" — 1 км/ч (задан в ТЗ прямо) —
  переиспользуется и для обнаружения остановки, отдельного числа в ТЗ для этого нет (явно
  задокументировано как допущение в коде). Окно из `JustDeparted` само гаснет через ~5 минут
  движения, но если за эти 5 минут случилась новая остановка — тут же показывается `Stopped`, не
  дожидаясь скрытия. Сигнал на 25 минутах стоянки — `onUpdate()` возвращает `true` ровно один раз
  за стоянку, повторно не срабатывает, пока не уехали и не встали заново. 7 тестов
  (`ArrivalDepartureTrackerTest.kt`), включая оба буквальных сценария из ТЗ-раскадровки.
- `Station.kt` — `nearestStationName()`: "место стоянки" для истории (название станции, если
  остановка внутри её границ, иначе км+пк форматирует вызывающий код). Настоящих границ
  вход/выход сигналов под рукой нет, поэтому это осознанное приближение — станция, если позиция
  в пределах допуска (по умолчанию 1500 м) от самой станции по `track_stations.json`, что обычно
  шире, чем "между входным и выходным" — задокументировано прямо в коде как известный разрыв с
  точной формулировкой ТЗ. 4 теста (`StationTest.kt`).
- В HTML-макете (`preview.html`) — две новые кнопки в шапке (⏱ окошко, 📋 история), сам оверлей
  окошка (непрозрачный чёрный фон, белый текст — специально НЕ через общую систему модалок
  `SUB_MODAL_IDS`, потому что график должен оставаться видимым и активным вокруг окна, а не
  перекрываться целиком) и полупрозрачная компактная панель истории. JS-версия
  `updateArrivalDeparture()` — прямой порт `ArrivalDepartureTracker.kt` 1:1. Добавлена демо-кнопка
  "Поезд едет/стоит" (не из ТЗ) — имитирует смену скорости, чтобы можно было увидеть окно в деле
  без реального GPS.
- **Подключено в реальном приложении** (`MainActivity.kt`) после того, как машинист посмотрел
  макет и подтвердил, что он верный. `TrackProfileView` теперь обёрнут в `FrameLayout` — окошко
  (`arrivalWindow` в `activity_main.xml`) сидит поверх графика сверху-слева тем же способом, что
  и в макете (непрозрачный чёрный фон, не отдельный экран). Кнопка `arrivalToggleButton`
  («Стоянка ⏱», в ряду рядом с «Параметры») показывает/скрывает окно — сама логика
  показать/скрыть не завязана на кнопку жёстко: окно и так появляется/пропадает по состоянию
  трекера (Hidden/Stopped/JustDeparted), кнопка лишь дополнительно прячет его вручную, если
  машинисту оно сейчас не нужно.
  - Средняя строка тикает раз в секунду через тот же `Handler`, что обновляет часы
    (`timeUpdater`) — не только из GPS-колбэка: если поезд стоит на месте, `GpsLocationProvider`
    (порог `minDistanceM=1f`) может вообще не прислать новую точку, а секундомер обязан идти
    независимо от этого. Каждый тик вызывает `arrivalDepartureTracker.onUpdate()` с последней
    известной скоростью (`lastSpeedKmh`, обновляется в GPS-колбэке из `location.speed`) — этим
    же тиком ловятся и оба чисто временных перехода (скрытие через ~5 минут, сигнал на 25-й
    минуте), а не только смена скорости.
  - Сигнал на 25 минутах стоянки — `ToneGenerator` (`TONE_PROP_BEEP2`, только звук, без
    отдельного аудиофайла — для разового технического бипа он не нужен, в отличие от голосовых
    оповещений раздела 6).
  - **История остановок пока не подключена к UI** — сама история копится (`arrivalDepartureTracker.history`,
    как побочный эффект работы автомата), но панели и второй кнопки в шапке для неё в реальном
    приложении ещё нет (в макете есть). Добавится отдельным шагом, если понадобится.

## Сборка

Проект — стандартный Gradle/Android Studio проект (Kotlin, minSdk 26).

```
./gradlew assembleDebug
```

Открыть в Android Studio: `File → Open` → выбрать папку проекта.

> В текущей среде разработки (песочница) нет доступа к `dl.google.com`/`maven.google.com`, поэтому
> здесь нельзя скачать Android SDK и собрать APK — соберите проект в Android Studio на своей
> машине.
