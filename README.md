# TrainDriverApp (рабочее название — «Крис»)

Android-приложение для машиниста локомотива (аналог УСАВП/ИСАВП-РТ). На экране устройства
приложение называется «Крис» (может ещё поменяться); `TrainDriverApp` — кодовое имя самого
проекта/репозитория, менять не стал, чтобы не переименовывать пакет и Gradle-модули без нужды.

## Что уже сделано (шаг 1)

Самый первый шаг: GPS показывает текущую координату в формате **км+пк**, без какого-либо
оформления экрана — просто крупный текст на чёрном фоне.

Как это работает:

1. `location/GpsLocationProvider.kt` — получает координаты через стандартный `LocationManager`
   (провайдер `GPS`), без Google Play Services и без интернета — приложение должно быть полностью
   автономным (ТЗ, раздел 2).
2. `route/RouteTrack.kt` — проецирует GPS-точку на ближайший отрезок полилинии пути и возвращает
   пикетаж (расстояние от начала маршрута в метрах).
3. `route/ChainageFormatter.kt` — переводит пикетаж в формат "км+пк". **Формула ниже —
   исправленная** (см. шаг 8): обычный км+пк по умолчанию — `км = floor(метры/1000)` (без +1),
   `пк = floor(метры_в_км / 100) + 1`; отдельно, по тапу на координату, включается формат
   КЛУБ-У — `км = floor(метры/1000) + 1` (это и есть формула с примерами из ТЗ:
   `0000.050 → 1км 1пк`, `6234.670 → 6235км 7пк` — она про КЛУБ-У, не про обычный км+пк).
4. `MainActivity.kt` — запрашивает разрешение на геолокацию и выводит результат в `TextView`.

### Важно: калибровка км — ПРИБЛИЗИТЕЛЬНАЯ, нужна проверка

У GPS-линии из OSM нет привязки к реальным номерам километров РЖД — только форма пути. У профиля
пути в PDF (`Хилок-Крм.pdf`, `Крм-Чернышевск.pdf` и т.д., которые ты прислал) есть реальные номера
км, но нет GPS. Пока сделано так:

- начало маршрута (ближайший к Хилоку узел линии) считается точкой **км 5930** — это число просто
  прочитано с левого края первой страницы `Хилок-Крм.pdf`, где начинается участок с станцией Хилок;
- построенная по OSM линия короче, чем разница реальных км по профилю (642.8 км против 659 км
  между Хилоком и Чернышевском) — это ожидаемо, т.к. OSM хранит сглаженную/упрощённую форму пути.
  Введена единая поправка на длину `659 / 642.8 ≈ 1.025` (`RouteTrack.HILOK_CHERNYSHEVSK_LENGTH_CORRECTION`),
  чтобы компенсировать это в среднем по всему маршруту;
- совпадение общей длины (642.8 км по факту против 659 км по профилю, расхождение ~2.5%) — хороший
  знак, что путь построен правильно (не перепутана ветка на разъезде и т.п.), но это не то же самое,
  что точная калибровка каждого пикета.

**Что нужно от тебя, чтобы довести до точности:** одна-две проверенные пары "GPS-точка ↔ реальный
км+пк" (например, встань на сигнале с известным км+пк и посмотри, что показывает телефон). По ним
можно будет поправить `HILOK_START_KM` и коэффициент коррекции и проверить, что ошибка не растёт
к концу маршрута.

Также пока не реализовано: выбор направления (чётное/нечётное) и различение правильного/
неправильного физического пути (ТЗ, раздел 3) — сейчас пикетаж всегда считается по одной линии.

## Шаг 3: разобраны постоянные ограничения скорости

Из `скорости все новые.xlsx` (набирался вручную с бумажных документов дороги, поэтому формат
неоднородный) вычленены постоянные ограничения скорости для основного пути на нашем перегоне,
для гружёных поездов серий 3ЭС5К/ВЛ85 — это данные для «ступенчатого графика скорости» (ТЗ,
раздел 7).

- Взяты 4 листа: `Хилок-КРМ`, `КРМ-Хилок`, `КРМ-Черн`, `Черн-КРМ` (по два на направление —
  чётное/нечётное, пикеты растут/убывают, см. ТЗ раздел 3). Остальные листы файла (`Хилок-ПЗВ`,
  `КРМ-Олов` и т.п.) — это другие перегоны, не наш маршрут, не трогали.
- Из каждой строки берётся диапазон км+пк (колонка «Станция/перегон») и скорость для 3ЭС5К/ВЛ85 —
  остальные колонки (скорость по стрелкам/приёмо-отправочным путям, обрывные места, проба
  тормозов, осмотр поезда, порожние вагоны) пока не трогаем, они для отдельных функций
  (пиктограммы, оповещения) и разберём их позже.
- Результат — `app/src/main/assets/speed_limits.json`, 411 диапазонов. В код ещё не подключено —
  экрана, который бы это показывал, пока нет.
- Сборка воспроизводима: `tools/parse_speed_limits.py "скорости все новые.xlsx" app/src/main/assets/speed_limits.json`.

### Важно про эти данные

- **Иерархия диапазонов.** У каждого перегона/станции есть «общая» строка на весь блок
  (например «Хилок - Гыршелун (5935 пк 3 - 5950 пк 7)» → 80 км/ч) и более узкие строки-исключения
  внутри неё (например «5942 пк 5 - 5943 пк 7» → 60 км/ч) — обе попали в список как есть. Значит,
  при использовании этих данных нужно сначала искать САМЫЙ УЗКИЙ подходящий диапазон и только
  если ни один не подошёл — брать общий. Логику выбора ещё не писал.
- **6 опечаток в исходном файле** (кириллические "З"/"б" вместо цифр "3"/"6" — например
  "6124 пк З", "б376") — скрипт их поправил, водитель подтвердил все шесть по бумажному
  оригиналу: `6123 пк2-6124 пк3`, `6277 пк10-6279 пк3`, `6292 пк8-6293 пк3`, `6053 пк3-6014 пк9`
  (Могзон - Тайдут), `6393 пк8-6376 пк10` (Размахнино - Зубарево), `6305 пк10-6302 пк3` (Тарская -
  Карымская).
- **Битая ячейка на участке 6159 пк 2 - 6162 пк 8** (лист Хилок-КРМ, в файле вместо числа стояло
  `'S()'`) — водитель подтвердил, что там 80 км/ч; исправление зашито в `KNOWN_CORRECTIONS` в
  скрипте, со ссылкой на то, что это подтверждено по бумажному документу, а не подобрано скриптом.
- **4 строки без понятной скорости** — не попали в итоговый файл, это станционные/стрелочные
  уточнения, чья скорость лежит в другой колонке (см. ниже про «Путь 4» и т.п.).
- **51 строка вида «Путь 4», «стр. №37», «съезд 5-7»** — это уточнения скорости для конкретного
  станционного пути/стрелки, без своего диапазона км+пк (он берётся из строки-заголовка станции
  выше). Не попали в файл — они не нужны для скорости по ходу главного пути, пригодятся позже для
  вкладки станций/путей, если понадобится.

## Шаг 4: разобраны условные предупреждения о жёлтом сигнале

Из `сигналы_желтый_чётное.xlsx` и `сигналы_желтый_нечётное.xlsx` — список правил вида «если
после сигнала [От] следующий сигнал [До] покажет жёлтый, скорость проследования не выше [X]
км/ч» (ТЗ, раздел 6 / «Условное предупреждение про жёлтый сигнал»). В отличие от файла со
скоростями, эти два размечены аккуратно, обычными колонками — разбор занял минуты, без
regex-эквилибристики и опечаток.

- 96 строк (чётное) + 61 строка (нечётное) = 157 — точно совпадает с числом из ТЗ.
- Все строки разобрались без проблем, пропусков и битых значений не нашлось.
- Результат — `app/src/main/assets/yellow_signal_warnings.json`, воспроизводится
  `tools/parse_yellow_signals.py yellow_signal_warnings.json <папка с исходными xlsx>`.
- 4 из 157 записей помечены «по неправильному пути» (`wrong_path: true`) — они срабатывают,
  когда состав идёт по неправильному физическому пути (ТЗ, раздел 3).

### Важно: не хватает привязки сигналов к км+пк

В этом файле сигналы названы литерами («Ч», «ЧМ2А», «т.11» и т.п.) и станциями/перегонами, но
**без** координаты км+пк — только длина блок-участка в метрах. Чтобы функция реально
срабатывала по GPS-позиции (при вступлении на блок-участок перед сигналом «До»), нужно ещё
знать, на каком именно пикете стоит каждый сигнал «От». Этого сопоставления сигнал → км+пк
пока нет нигде в присланных данных.

**Решение:** делаем эту привязку не сейчас отдельно, а вместе с главным экраном (ТЗ, раздел 7) —
там всё равно придётся построчно разбирать те же профили пути в PDF (ступенчатый график,
пиктограммы, рельеф), и координаты сигналов естественно появятся по ходу дела.

Термины сигналов (от машиниста, для справки):
- **т.NN** («точки») — перегонные светофоры без буквенной литеры; номер убывает к станции по
  правильному пути (14, 12, 10... чётное; 15, 13, 11... нечётное, см. ТЗ раздел 4).
- **Ч / Н** — входные сигналы станций (по правильному пути); **ЧД / НД** — то же, по
  неправильному пути.
- **ЧМ / НМ** — маршрутные сигналы, делят станцию на участки (горловины, парки).
- **Ч2 / Н1** (буква + число, без «М») — выходные сигналы станций.

## Шаг 5: разобраны точки пробы тормозов

Из `Пробы_тормозов.xlsx` (листы `Хилок-КРМ` и `КРМ-Черныш` — остальные листы того же файла
покрывают другие участки дороги, не наши) — список точек, где нужно выполнять пробу тормозов
(ТЗ, раздел 6, оповещение «Впереди проба тормозов!» за 2000 м до точки).

- Результат — `app/src/main/assets/brake_tests.json`, 42 точки (26 чётных + 16 нечётных, из
  них 5 — для сдвоенного поезда). Воспроизводится
  `tools/parse_brake_tests.py "Пробы_тормозов.xlsx" app/src/main/assets/brake_tests.json`.
- Данные чистые, без опечаток и пропусков — разбор занял пару минут, как и с сигналами.

### Как это устроено (пояснения машиниста)

- **км+пк в списке — координата самой пробы**, а не точки объявления; объявлять нужно за
  2000 м до неё (это уже знали из ТЗ, теперь подтверждено).
- **Скорость вида «55/60»** — это диапазон (55–60 км/ч), внутри которого проба тормозов
  засчитывается; вне диапазона нужно ждать следующую точку. Если диапазонов несколько
  («45/50 55/60 65/70» на «Гонгота-Сохондо») — подходит любой из них.
- **Строки «(сдвоен.)»** — отдельная, другая точка пробы специально для сдвоенного поезда
  (не тот же километр с другим текстом объявления). Как машинист будет отмечать в приложении,
  что поезд сдвоенный, — пока не решено, будет отдельная настройка позже.
- **Этот список — источник истины.** Если режимная карта (профиль пути в PDF) показывает пробу
  тормозов в другом месте — верить нужно этому списку, а не карте: на картах пробы бывают
  указаны неправильно.

## Шаг 6: логика направления и правильного/неправильного пути

`route/DirectionSelection.kt` реализует таблицу из ТЗ (раздел 3 / «УСАВП-аналог_ИТОГ.pdf»
раздел 4): машинист вручную выбирает направление (чётное/нечётное) и физический путь (1 или
2) — из этой пары выводится:

- **правильный/неправильный путь** — чётное+путь2 и нечётное+путь1 правильные, остальные два
  сочетания неправильные;
- **какой датасет использовать** (поле `direction` в speed_limits.json /
  yellow_signal_warnings.json / brake_tests.json) — на практике сводится к тому, что путь 1
  всегда означает нечётный датасет, путь 2 — чётный, независимо от выбранного направления;
- **растут пикеты или убывают** — зависит только от направления (чётное — растут, нечётное —
  убывают), не от пути.

Km+пк по GPS при этом никак не меняется в коде в зависимости от направления — `RouteTrack`
просто отражает физическую позицию на пути, которая сама по себе растёт или убывает в
зависимости от того, куда реально едет поезд. Направление здесь нужно только чтобы понять,
какой из двух датасетов (собранных отдельно для чётного/нечётного) сейчас использовать при
поиске скоростей/сигналов/проб тормозов — см. следующий шаг, там это уже подключено для
скоростей.

Пока сделаны только две кнопки-переключателя на временном экране (не финальный вид, просто
чтобы проверить логику): «Чётное/Нечётное» и «Путь 1/Путь 2», плюс строка с результатом
(«Путь правильный, датасет: чётный, пикеты растут»). По умолчанию — чётное, путь 2.

## Шаг 7: главный экран, первый срез — линейка и ступенчатый график скорости

Начали главный экран (ТЗ раздел 7) с того, на чём держится всё остальное — километровая/
пикетная линейка и ступенчатый график постоянных ограничений скорости, поверх которых потом
встанут сигналы, пиктограммы и профиль рельефа.

- `route/SpeedLimit.kt` / `SpeedLimitAssetLoader.kt` — читают speed_limits.json, переводя
  км+пк в метры через новую `ChainageFormatter.toMeters()` (обратную к `format()`).
- `route/SpeedLimitResolver.kt` — по позиции (в метрах) и направлению возвращает действующее
  ограничение; если подходит и общая, и более узкая строка-исключение (см. шаг 3) — побеждает
  самая узкая, как и было задумано.
- `ui/TrackProfileView.kt` — кастомная View: рисует ступени (серая заливка от 100 км/ч вниз
  до значения лимита — как в ТЗ, «не снизу вверх»), километровую сетку с номерами км по
  центру столбца (как на профилях пути), пикетные деления и вертикальный маркер позиции
  поезда. Окно обзора — 3000 м позади / 5000 м впереди головы, как в официальном описании
  экрана ИСАВП-РТ (`основное_окно_сокр.pdf`).
- Подключено в `MainActivity` — при каждом обновлении GPS обновляется и позиция на графике;
  при переключении направления/пути (шаг 6) — какой датасет (чётный/нечётный) показывать.

### Исправление: сверка с реальным макетом (раздел 14 ТЗ)

Первая версия этого шага была построена только по текстовому описанию раздела 7 — я не
прочитал страницы 8–14 самого первого ТЗ-файла (14 страниц всего), где как раз лежит раздел
14 "Приложение: полный набор изображений макетов" с реальными картинками главного экрана.
Из-за этого первая версия сильно недотягивала до макета: не было шапки, чисел на самих
ступенях, шкалы скорости слева, нижней строки статуса. Прочитал эти страницы, поправил:

- `SpeedLimitResolver.findNextChange()` — ищет ближайшую впереди точку, где меняется
  скорость (нужно для ячейки "V=.../S=..." нижней строки статуса).
- `TrackProfileView` — добавлены шкала скорости слева (100/80/60/40/20) и число скорости
  прямо на каждой ступени (крупным белым по центру), как на макете.
- Шапка (`MainActivity`, `activity_main.xml`) — координата слева, время МСК и местное справа
  (местное — из часового пояса телефона, обновляются раз в секунду по-настоящему, не заглушка).
- Нижняя статусная строка (5 ячеек по ТЗ): Vф — настоящая скорость по GPS; V=/S= — настоящий
  расчёт через `findNextChange`; Уклон/Голова/Хвост — пока "—", для них нужны данные о
  рельефе пути и о км+пк сигналов, которых ещё нет (см. шаг про сигналы).
- Живой HTML-макет в чате обновлён тем же способом — можно посмотреть без сборки APK.

ограничений (у нас пока и нет данных о временных ограничениях — только постоянные), уклон/

будем добавлять поверх этого фундамента по одному.

### Внешний вид проверен только в браузере, не на Android

В этой среде разработки нет Android SDK (см. «Сборка» ниже), поэтому саму Kotlin-вёрстку
(`TrackProfileView`, `activity_main.xml`) я не видел вживую — только логика прошла юнит-тесты.
Но общую композицию экрана я больше не показываю вслепую: HTML-версию в чате рендерю headless-
браузером (Chromium) и сам смотрю на скриншот перед тем, как публиковать ссылку — так нашлась
и исправилась ошибка на 1 км из шага 8. Всё равно собери и запусти на своём Realme при
возможности — Android-вёрстка может выглядеть иначе, чем HTML-копия.

## Шаг 8: исправлен формат км+пк — путали с КЛУБ-У

Нашлась серьёзная ошибка: в ТЗ (раздел 7) написано "Координата (км+пк, **по тапу
переключается в формат КЛУБ-У**)" — то есть это ДВА РАЗНЫХ формата. Формула с примерами
(`km = floor(значение)+1`, `0000.050 → 1км 1пк`) — это именно формат **КЛУБ-У**, отдельный,
включаемый только по тапу. А обычный км+пк (тот, что должен быть по умолчанию, и тот, которым
записаны все таблицы — например "Хилок (5932 пк 7 - 5935 пк 3)" в speed_limits.json) — БЕЗ
+1: `км = floor(метры/1000)`.

Раньше `ChainageFormatter` использовал формулу КЛУБ-У как единственную и универсальную —
из-за этого:
- координата в шапке показывала км на 1 больше реального;
- что важнее — `SpeedLimitAssetLoader` использовал ту же (неверную) формулу для перевода
  км+пк из speed_limits.json в метры, поэтому весь график ограничений скорости был физически
  сдвинут на 1000 м относительно реальной GPS-позиции. Это, видимо, и была основная причина
  «совсем не похоже на ТЗ» — график и координата не совпадали друг с другом даже там, где
  форма была правильной.

Исправлено:
- `ChainageFormatter.format()` — теперь обычный км+пк (без +1), формат по умолчанию;
- `ChainageFormatter.formatKlubU()` — новый метод, старая формула с +1, для формата КЛУБ-У;
- `ChainageFormatter.toMeters()` — тоже без +1/-1, обратное к обычному км+пк (так как именно
  в этом формате записаны все остальные данные);
- клик по координате в `MainActivity` теперь переключает обычный км+пк / КЛУБ-У, как в ТЗ;
- километровые подписи на графике (`TrackProfileView`, HTML-превью) — тоже без +1.

## Сборка

Проект — стандартный Gradle/Android Studio проект (Kotlin, minSdk 26).

```
./gradlew assembleDebug
```

Открыть в Android Studio: `File → Open` → выбрать папку проекта.

> В текущей среде разработки (песочница) нет доступа к `dl.google.com`/`maven.google.com`, поэтому
> здесь нельзя скачать Android SDK и собрать APK — соберите проект в Android Studio на своей
> машине.
